# Failure-Mode Catalog (test-facing)

Drafted in phase 03; mirrors [../architecture/failure-handling.md](../architecture/failure-handling.md) (source of
detection/recovery design). Owned by test-engineer: every row gains a **real test reference** as stages land; the
"Covered by" column is filled in during phases 04–05 and audited at each stage gate. Test strategy:
[testing-standards.md](testing-standards.md). Requirements trace: [../spec/requirements.md](../spec/requirements.md) §3.

Status legend: `planned` (test named, not written) → `covered` (test exists, referenced) → `hardened` (also exercised
in fault-injection/load stages).

| F18 | An out-of-range `limit` reaches the catalog, or means two different things per route | api, catalog | contract: every list route answers 422 for `-5`, `0`, `501` and `10**9`; the boundary values `1` and `500` are accepted; an oversized limit never reaches the catalog; the bound is asserted in OpenAPI (`tests/contract/test_api_adversarial.py::TestPaginationBounds`) | Baseline | covered: six routes hand-rolled a 1..500 check while four silently clamped to 200, so a client could not tell a truncated page from a complete one and the UI route's clamp defended a browser caller that never sends the parameter; the bound now lives in one `Limit` alias in the signature, which is also what OpenAPI documents. Found by an API-consistency sweep 2026-09-30 |
| F19 | Port preflight reads a variable the application ignores | scripts | unit: `port_from_env()` equals `Settings().api_port` under `DE_API_PORT`, and `DE_PORT` is refused (`tests/unit/test_port_scripts.py`) | Baseline | covered: the advice `DE_PORT=8001 just run` named a port the server would not bind; found by an operator reading the error text 2026-09-30 |
| F20 | Theme swap leaves a second stylesheet after ours, re-enabling the vendor glow | web | browser: `just ui-audit` asserts one theme sheet, loaded before `faultlined.css`, across 44 page loads (4 themes x 11 pages) and finds no computed `text-shadow`; unit: the probe is removed on both paths and the served link order is pinned (`tests/unit/test_web_frontend.py`) | Baseline | covered: the probe link appended to `<head>` was never removed, so the phosphor `text-shadow` won the cascade until a full reload; found by an operator 2026-09-30 |
| F21 | A truncated fixture download is accepted as complete, or errors the run | test fixtures | unit against a local HTTP server: a short body, a reset mid-transfer and a 404 all raise `FixtureUnavailable` and leave no file or `.partial` behind; a body with no `Content-Length` is still accepted (`tests/unit/test_fixture_download.py`) | Baseline | covered: `IncompleteRead` is an `http.client` exception and escaped the retry entirely, so a CDN reset surfaced as a build failure; the real-dataset assertions now cross-check the dataset's own index instead of copied constants |
| F22 | A job is stranded in `running` forever when its worker dies | jobs, catalog | integration against real SQL: an abandoned job is requeued, is claimable again through the normal path, a job inside the window is left alone, and one with no retry budget left is failed rather than stranded (`tests/integration/test_crash_recovery.py`) | Baseline | covered: `reap_expired_deadlines` existed but no caller ever invoked it, so F6 deadlines were never enforced on a job already running; and a job with no `deadline_seconds` whose worker was killed had no recovery path at all, since `claim_job` selects only `queued`. Fixed by calling both reapers from the worker loop and adding `reap_orphaned_jobs`. Found by a fault-tolerance audit 2026-09-30 |
| F23 | A transient database outage ends the worker's life | jobs, cli | unit: the loop keeps calling `process_one` past two consecutive `connection refused` failures instead of propagating, and a failing reaper sweep does not stop it either (`tests/unit/test_cli.py`) | Baseline | covered: `claim_job` runs before the per-job `try`/`except` in `process_one`, so a lost connection propagated out of `_worker_loop` and took the process down, leaving the queue unprocessed until someone restarted it. Fixed by catching at the loop and backing off. Found by the same audit 2026-09-30 |
| F24 | A runaway query pins a connection until the API exhausts its threads | catalog | integration against real SQL: `pg_sleep(30)` is cancelled with `QueryCanceled`, the failure does not escape the context manager, and the next connection is unaffected (`tests/integration/test_statement_timeout.py`) | Baseline | covered: `connect` bounded only the connect phase, so an unbounded query held a connection with no ceiling. A 15 s `statement_timeout` now rides on the same `psycopg.connect` call. Found by the same audit 2026-09-30 |
| F25 | An integration test asserts against a global list in an accumulating shared database | test infrastructure | integration: the crash-recovery tests create one job each and delete it, never drain the shared queue, and sort ahead of existing rows by a computed threshold rather than a constant; the real-dataset and curation tests fetch their own row instead of scanning a capped page (`tests/integration/test_crash_recovery.py`, `test_real_dataset_ingest.py`, `test_curation.py`) | Baseline | covered: the real-dataset test asserted its episode appeared in `list_episodes(limit=500, state="quarantined")` while the shared test database had already accumulated 509 quarantined episodes, so it failed about one run in eight; the crash-recovery tests also claimed and abandoned up to 200 foreign jobs reaching for their own. Both asserted on state that grows without bound instead of on the row under test. Found by running the suite repeatedly instead of trusting one green run, 2026-09-30 |

Additional classes required by [../spec/00-original-specification.md](../spec/00-original-specification.md) §6 to be
disaggregated here as implementation reveals them: network failure (S3-tier trigger era), duplicate *data* (same
episode ingested from two sources — distinct from F4), invalid API pagination/cursor misuse.

Audit rule: a stage gate may not claim "failure-mode catalog covered by tests" (definition-of-done stage 3) while any
row is `planned`.
