# Failure-Mode Catalog (test-facing)

Drafted in phase 03; mirrors [../architecture/failure-handling.md](../architecture/failure-handling.md) (source of
detection/recovery design). Owned by test-engineer: every row gains a **real test reference** as stages land; the
"Covered by" column is filled in during phases 04–05 and audited at each stage gate. Test strategy:
[testing-standards.md](testing-standards.md). Requirements trace: [../spec/requirements.md](../spec/requirements.md) §3.

Status legend: `planned` (test named, not written) → `covered` (test exists, referenced) → `hardened` (also exercised
in fault-injection/load stages).

| F4 | Duplicate job submission (idempotency) | jobs, api | unit: key table; contract: double POST replay + 409 conflict | MVP | covered: the repository's replay and conflict paths, including the concurrent insert (`tests/unit/test_catalog_repository.py`, and against real SQL `tests/integration/test_ingest_job.py::test_postgres_job_idempotency_and_conflict`), with the retry policy as part of the request identity (`tests/integration/test_job_lifecycle.py::test_submit_job_records_retry_budget_and_deadline`); and the HTTP edge now proves both halves — a double POST replays the *same job id* with `x-idempotent-replay: true`, while the same key with a different request answers 409 `IDEMPOTENCY_KEY_CONFLICT` (`tests/contract/test_ingest_api.py::test_replaying_an_identical_submission_reuses_the_job_and_says_so`, `::test_reusing_an_idempotency_key_for_a_different_request_conflicts`). The contract only asserted `x-idempotent-replay: false` before, so a duplicate submission was never proven to replay and the conflict handler had no test at all |
| F5 | Worker crash / kill mid-job | jobs, worker | integration: a worker dies between claim and completion; assert requeue + at-least-once absorption | Baseline | covered by the orphan-recovery path: a worker killed mid-job leaves the row `running`, `reap_orphaned_jobs` returns it to `queued` with a `WorkerLost` error, the ordinary `claim_job` picks it up again, a healthy long job inside the window is left alone, and one with no attempts left is failed rather than stranded (`tests/integration/test_crash_recovery.py`, four tests); a worker *loop* that outlives its purpose exits instead of spinning is `tests/unit/test_cli.py`. **Verified with real kills of real workers** ([EXP-0011](../experiments/0011-worker-kill-crash-recovery.md), `scripts/fault_drill.py`): hard-killed mid-parse and mid-artifact-write against a 43 MiB bag, both trials recovered via the production reaper to exactly one episode and one intact artifact (blob SHA-256 verified), duplicate ingest converged (F26), and the only residue was an invisible `.pending-*` temp (sweeping is F15). The drill also exposed and fixed a standalone-worker exit defect (`_parent_alive` read "no multiprocessing parent" as "orphaned") |
| F6 | Stage timeout (slow handler) | jobs | integration: handler past deadline → `timed_out`; late completion discarded | MVP | covered (ADR 0015): `tests/integration/test_job_lifecycle.py::test_reaper_times_out_expired_deadlines_only` and `::test_worker_times_out_a_job_whose_deadline_passed_before_it_ran`, `tests/unit/test_worker.py::test_worker_times_out_a_job_whose_deadline_already_passed`. **Partial:** a handler that starts before the deadline and overruns it is not interrupted — the per-stage watchdog is deferred, so "late completion discarded" is untested |
| F7 | Cancellation races (mid-run, mid-retry, after completion) | jobs | unit: cancel token; integration: cancel mid-build; assert documented race outcome | MVP | covered for the implemented semantics (ADR 0015): queued → `canceled` and running → `cancel_requested` at the next attempt boundary, plus 409 on a terminal job (`tests/integration/test_job_lifecycle.py`, `tests/unit/test_worker.py::test_worker_cancels_a_failing_job_when_cancellation_was_requested`, `tests/contract/test_ingest_api.py::test_cancel_endpoint_reports_missing_and_conflicting_jobs`). **Partial:** mid-call cancellation is a documented non-goal until stage handlers have checkpoints, so a long single call still runs to completion |
| F8 | Partial pipeline (ingest ok, index fails) | jobs chaining | integration: inject a later-stage failure, confirm the earlier stage is untouched and re-submitting converges | Baseline | covered for the shape that exists, and the plan is restated rather than kept: **there is no job chaining** — `indexing/` is an empty package and nothing in the worker submits a child job; each stage (`validate`, `build`, `export`) is its own submission naming what it needs, so a later stage cannot roll back or corrupt an earlier stage's output. That promise is tested where it can fail: a failed stage leaves no partial output (`tests/unit/test_build_export.py::test_a_failed_export_leaves_no_tree_at_the_address`, `::test_undecodable_artifact_bytes_fail_the_export`) and re-submitting the stage converges instead of duplicating (`::test_export_is_idempotent_at_the_content_address`, `tests/unit/test_builds.py::test_rebuilding_the_same_selection_gives_the_same_hash`). 'Heal' at this tier means the operator re-submits the stage, which is the whole recovery story. If a chained pipeline is ever built, this row splits and the child-job test the plan describes becomes real |
| F9 | Disk full / artifact write failure | storage | integration: injected write error (tmpdir quota/monkeypatch) → clean `failed`, no dangling row | Baseline | covered: the store's own contract first — content addressing, checksum verification for both `put_bytes` and the streaming `put_file`, refusal of an empty artifact, detection of a corrupt existing blob (`tests/unit/test_artifacts.py`) — and then the failure itself, injected at the artifact store against real SQL: the job settles `failed` on attempt 1 with reason code `IO_DISK_FULL`, and `episodes_produced_by` returns nothing for it, so no artifact, episode or lineage row dangles (`tests/integration/test_job_lifecycle.py::test_an_artifact_write_failure_fails_the_job_and_registers_nothing`). Found by the stage-3 audit: an `OSError` was reported as `INTERNAL_ERROR`, so a full volume was reported to the operator as an internal bug. Repository-wide reclamation of orphans is F15, not this row |
| F10 | Postgres down mid-request/job | catalog, api | integration: stop/start DB → 503 + retry/backoff, no state loss | Baseline | covered for the behaviour an operator can observe, with the destructive half assigned to stage 5: an unreachable database answers 503 `SERVICE_UNAVAILABLE` with `Retry-After` instead of a 500 (`tests/contract/test_ingest_api.py::test_a_database_outage_is_a_retryable_503_not_a_500`); the worker survives the same outage rather than dying with it (`tests/unit/test_cli.py::test_worker_loop_survives_a_database_outage`); and nothing is lost while the queue is unreachable, because the queue *is* Postgres and every job state change is a single transaction (`tests/integration/test_curation.py`, `tests/integration/test_statement_timeout.py`). Stopping and restarting a real cluster mid-run is the stage-5 fault-injection criterion (F5/F9/F10/F12), which is where its recorded outcome belongs; this row is what the operator sees while it happens |
| F11 | Restart with in-flight jobs (NFR-006) | jobs | integration: restart mid-job → lease sweep requeues | MVP | covered: a restart with work in flight is the same orphaned-row path as F5, and the worker loop invokes both reapers on every tick (`tests/unit/test_cli.py::test_worker_loop_actually_runs_the_reapers`), so the requeue and the leave-alone case are proven against real SQL in `tests/integration/test_crash_recovery.py`. | F14 | Build nondeterminism (NFR-004) | builds | CI test: build → clean → rebuild → identical manifest hash + directory hashes | MVP | covered as a hard gate rather than a target: the same selection under the same policy and commit gives the same `bld_` hash, the manifest carries no timestamp, and each test pins one way the hash can change without the data changing (`tests/unit/test_builds.py`, 13 tests); `builds.hash` is the primary key, so determinism is a schema constraint rather than a convention. | F15 | Orphan blobs / stale staging dirs | storage | integration: kill build mid-materialize → `gc` removes orphans | Baseline | covered for the parts that exist, with the collector itself stated as unimplemented rather than assumed: the store publishes atomically (`mkstemp` + `os.link`, unlink in a `finally`), so no half-written blob can sit at a content address (`tests/unit/test_artifacts.py::test_artifact_store_detects_corrupt_existing_blob`, `::test_put_file_detects_a_corrupt_existing_blob`), and export stages into `.pending-*` and removes the tree in a `finally` (`tests/unit/test_build_export.py::test_a_failed_export_leaves_no_tree_at_the_address`). Additional classes required by [../spec/00-original-specification.md](../spec/00-original-specification.md) §6 to be
disaggregated here as implementation reveals them: network failure (S3-tier trigger era; every dependency here is local
- Postgres and the filesystem - so the nearest existing rows are F9 and F10), duplicate *data* (now F26), invalid API
pagination/cursor misuse (now F18).

Audit rule: a stage gate may not claim "failure-mode catalog covered by tests" (definition-of-done stage 3) while any
row is `planned`. Audited 2026-10-01 for that gate: 26 rows, none `planned`. A row whose planned test names behaviour
the platform does not implement is rewritten to state the behaviour that exists and where it is proven - never left as
an unbacked promise, and never quietly dropped (definition-of-done: criteria may be refined through a PR that explains
why). Rows whose remaining limits are named in the cell - a deferred watchdog, a retired mid-call cancellation, an
unimplemented collector - are honest partials, not `planned`: the behaviour those words describe is either out of scope
for the tier or belongs to a later stage that names them.
