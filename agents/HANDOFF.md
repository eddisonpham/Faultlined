## 1. Problem

Local-first robot episode data engine: ingest, validate, curate and build reproducible robot datasets (MCAP / LeRobot) with lineage for ML workloads. The platform is the product; models are workloads. See [problem](spec/problem.md), [requirements](spec/requirements.md).

## 2. Architecture

- Python modular monolith, FastAPI API, PostgreSQL catalog and job queue, one separate worker process.
- Content-addressed local filesystem artifact store, stdlib JSON logging, psutil host snapshots with optional NVML.
- Path: API submit to Postgres queue to worker to canonical JSON artifact to episode/lineage catalog to API read.
- Known gaps in the foundation: schema init is inline idempotent DDL rather than migrations; artifact writes and catalog writes are not one cross-store transaction.
- Reading: [overview](architecture/overview.md), [data flow](architecture/data-flow.md), [components](architecture/components.md), [storage](architecture/storage.md), [repo layout](architecture/repo-layout.md).

## 5. Implementation status

### Working

- **Job lifecycle**: submission with `max_attempts` and `deadline_seconds`, atomic claim, cooperative cancel, deadline sweep, dead-worker recovery, terminal-vs-retryable failure classification ([ADR 0015](decisions/0015-cooperative-job-lifecycle.md)). The reapers run from the worker loop and a database blip backs off instead of ending the process.
- **Ingest, both chosen formats**: `ingest_source` jobs over a sniff-based reader registry. LeRobot v2.1 and v3.0, verified end to end against real Hub datasets. MCAP as a second registry entry with no core change ([ADR 0022](decisions/0022-mcap-ingest-reader.md)). Episode identity is `(source_hash, episode_key)`, so many episodes in one shard each get a catalog row while the file is stored once.
- **Validation**: hashed JSON profiles, a 7-rule engine, quarantine and re-validate without re-ingest ([ADR 0016](decisions/0016-json-validation-profiles.md)).
- **Quality signals**: movement, jerk, stall ratio, length z-score, temporal integrity, verdict on the median judged dimension. Non-finite input stops the analysis instead of poisoning dataset statistics; all three readers supply a clock ([ADR 0023](decisions/0023-quality-metrics-honesty.md), which amends ADR 0018).
- **Builds**: manifest hashed alone is the build identity, membership in `build_episodes`, graph in `lineage_edges`, reverse lineage at `GET /api/v1/episodes/{id}/builds`. NFR-004 asserted by 13 tests ([ADR 0007](decisions/0007-lineage-and-run-records.md)).
- **LeRobot v3 export of a build**: an `export` job writes the build out as a real v3 dataset directory (`meta/info.json`, per-episode index shards, `data/chunk-*/file-*.parquet` with global row ranges reindexed per episode), so the engine hands a training script files rather than a manifest ([ADR 0025](decisions/0025-lerobot-v3-export-of-builds.md), `tests/unit/test_build_export.py`, `tests/unit/test_worker_export.py`).
- **Run intelligence**: runtime metrics emitted at call sites, aggregated into percentiles and time series, served at `GET /api/v1/metrics` ([ADR 0017](decisions/0017-runtime-metrics-aggregation.md)); episode catalog, quality summary, job reports and export manifests; measured one workload per process ([ADR 0019](decisions/0019-benchmark-workload-isolation.md)).
- **Curation**: named slices that recompute membership on read, a slice impact view attributing every drop, and a read-only failures view. Vocabulary shared in `data_engine/curation.py` ([telldown plan](implementation/telldown-plan.md)).
- **Monitoring**: deterministic notifier, eleven rules, per-scope EWMA and median-MAD control limits over a versioned 26-feature vector, completion contracts, fingerprint dedup, cooldown, evidence and severity gates, hard alert budget. No model, no LLM call, no network in the detection path ([ADR 0020](decisions/0020-deterministic-monitoring-notifier.md), [plan](implementation/automated-monitoring-plan.md)).
- **Curated-layer redundancy (the curation programme opens here, 2026-10-07)**: every episode carries a **behavioural fingerprint** assembled from what ingest already computed - the motion trace, the per-dimension normalised motion character, and the stall/gap fractions - so "are two of my episodes the same behaviour recorded twice" is answered by a pure function of the stored rows, with no embedding model, no numerical library, no artifact read and no network ([ADR 0032](decisions/0032-behavioural-fingerprints.md)). `GET /api/v1/builds/{hash}/redundancy` and a section on `/ui/builds/{hash}` report the build's distinct versus near-duplicate episodes, each collapsed pair's distance and the component that dominated it. It **proposes and never removes**, and no fingerprint enters a build's identity. Calibrated by measurement against planted re-recordings: precision 0.826 / recall 0.394 at threshold 0.04, replacing the 0.10 it first shipped (precision 0.084 - the measurement invalidated the default); cost 218 ms p50 read+score at the 500-episode bound ([EXP-0019](experiments/0019-behavioural-fingerprint-calibration.md)). **No precision or recall is claimed for real robot data** - the corpus is synthetic and the real fixtures have no duplicate labels (backlog B-021). **The end-to-end claim was then walked as an operator** ([EXP-0020](experiments/0020-curation-ab-end-to-end.md)): over 24 behaviours x 4 takes = 96 episodes, through `POST /api/v1/jobs` and the redundancy route only, the arm that builds the report's representatives exported **330 022 bytes / 51 files against 1 315 547 / 195** - 25 % of the control - while retaining **24 of 24 planted behaviours**. The first attempt failed on the open empty-profile trap (`profile: {}` passes the schema, the handler refuses it) and reproduced it live. Landscape and the full idea set: [platform research](research/2026-10-07-platform-landscape-and-curation.md), [curation ideas](research/2026-10-07-curation-idea-improvements.md).
- **Build coverage (the curation programme's slice 2, 2026-10-07)** answers the question that drill exposed: the treatment build is *narrower*, and nothing could say in what way. `GET /api/v1/builds/{hash}/coverage` and a `Coverage` section on the same page report what the build holds on each axis the catalog already persists - task normalised through the vocabulary, embodiment, format, quality verdict - and what its catalog holds instead, as a **gap list rather than a score**, computed on read with nothing stored ([ADR 0033](decisions/0033-build-coverage.md)). Task gaps are drawn from the operator's own vocabulary, so a label they named and never recorded is reported as missing rather than not existing. It is bounded by construction (20 values and 20 gaps per axis, each with its true total and a truncation flag) and it **advises without gating**: no coverage figure enters a build's identity and no build is refused for a gap. Measured ([EXP-0021](experiments/0021-build-coverage-cost-and-what-it-sees.md)): **31 rows and 2 221 -> 2 296 B of payload at 100, 1 000 and 10 000 episodes** - against `quality/summary`'s 2.2 MiB at the same scale - with 126.0 ms read plus fold at 10 000 episodes (the pure fold is 0.26-0.34 ms; two `connect()` calls are most of the rest, now backlog **B-022**). On the EXP-0020 A/B it **independently confirms the curation claim** from a different source: the compacted build holds the same 28 distinct axis values as the control at 25 % of the episodes, while showing plainly that coverage is a guard on a curation step rather than the detector of its saving (the two arms' per-axis distributions are identical).
- **Task vocabulary (the source of truth for task strings)**: entries with stable content-derived ids and human-approved labels, mappings from raw task strings onto them, and an unmapped queue that is a *query* over episodes minus mappings so it cannot drift. Ingest auto-maps only on exact extracted-core equality with exactly one entry. Merges, splits, renames, maps and dismissals are recorded events with an exact compensating undo. The core-extraction measurement is unchanged and still the grouping key ([ADR 0026](decisions/0026-cluster-proposals.md), [ADR 0029](decisions/0029-task-vocabulary-first.md), `tests/unit/test_vocabulary.py`, `tests/unit/test_cluster_ranker.py`, `tests/integration/test_vocabulary.py`, `tests/contract/test_vocabulary_api.py`).
- **Cluster proposals (frozen archive)**: `GET /api/v1/clusters` and `/clusters/{key}` still answer reads; `rebuild`, `review`, `confirm` and `release` answer 410 Gone; `/ui/clusters*` redirects to `/ui/vocabulary`. The tables are dropped by a later forward-only migration after one release. `catalog/clusters.py` is still there in full — A6 trims it. Note the read is a *live* computation over every episode's extracted core (416.8 ms p95 at 10k, [EXP-0015](experiments/0015-feature-latency-at-three-scales.md)), so "frozen" currently describes the mutations and not the cost.
- **Monitoring is scheduled (2026-10-06).** The worker loop evaluates one window every 60 s (`MONITOR_INTERVAL_SECONDS` = the notifier's own window) inside `PostgresCatalog.monitor_lease()`, a session-scoped advisory lock, so a pool of N workers produces one tick per interval rather than one each ([ADR 0031](decisions/0031-monitor-scheduling.md)). A scheduled tick now opens a real incident without anyone POSTing the route, and costs 249.5 ms p50 / 435.1 ms p95 — inside EXP-0016's 349–407 ms band and roughly 0.4 % of a core at the 60 s cadence ([EXP-0018](experiments/0018-monitor-scheduling.md)). `POST /api/v1/monitoring/tick` stays as the on-demand probe and deliberately does not take the lease. Running the real deployment found and fixed a related honesty defect: `/api/v1/monitoring/health` answered from the API process's own memory, so it reported `last_tick_at: null` and `blind: no` while the worker was ticking; both facts are now read back from the shared metric sink, and `blind: null` (no tick anywhere yet) is distinct from `blind: false` ([ADR 0031 amendment](decisions/0031-monitor-scheduling.md)). That read-back is one bounded tail read per `health()` call, not two: `last_tick_at` and `blind` used to parse the same window separately, which cost 42 ms p50 on a 5k-record sink and 97 ms at the 20k bound, half of it duplicated, on a page that polls. Detection accuracy is still unmeasured (B-016); incidents now exist to measure it against.
- **Operator UI**: server-rendered, works with JavaScript disabled, visible failure policy in one client runtime, HTML error pages ([ADR 0014](decisions/0014-minimal-ui-server-rendered.md), [ADR 0021](decisions/0021-frontend-instrument-pass.md), [ADR 0024](decisions/0024-observability-visual-surface.md)). **The stated loop is completable without a JSON call** (2026-10-06): ingest from `/ui`, validate on `/ui/episodes`, build on `/ui/builds`, export from `/ui/builds/{hash}`, and save a slice on `/ui/slices`, all through the same Pydantic models the API uses. `/docs` and `/redoc` removed; `/openapi.json` kept for the drift gate. ## 6. Known technical risks

1. **The committed baseline is a regression tripwire, not a target.** Synthetic ingest P50 0.6084 ms, 10 trials, 0 failures at `f7ffbeb`; observed run-to-run spread about 24%. Comparison requires a byte-identical hardware profile, so the harness refuses to compare elsewhere.
2. **Crash consistency.** Artifact publication and catalog writes are separate transactions. Worker crash recovery, leases and orphan GC are future work.
3. **No detection-accuracy figure exists for the notifier.** It needs the full [Â§6](implementation/automated-monitoring-plan.md) fault-injection campaign with clean-replicate null bands (backlog B-016). No precision or recall is claimed anywhere.
7. ~~**The failure message persisted on a failed job is the literal string `"job handler failed"`.**~~ **Closed 2026-10-06:** `jobs/worker.py::_error_message` persists the handler's own exception type, a one-line length-capped credential-scrubbed message, and the reason code; `"job handler failed"` survives only as the no-text fallback (ADR 0015 amendment, [EXP-0014](experiments/0014-foreign-data-ingest-corpus.md) D3 closure).
8. ~~**A non-finite channel statistic fails the whole episode.**~~ **Closed 2026-10-06:** readers count non-finite samples instead of accumulating them, `finite_or_none` keeps every non-number out of `jsonb` (vectors sanitized element-wise), and a deterministic `psycopg.errors.DataError` is terminal with reason code `CATALOG_WRITE_REJECTED` (ADR 0023 amendment, EXP-0014 D2 closure).
9. ~~**A topic whose name contains `grip` silently voids an episode's motion verdict.**~~ **Closed 2026-10-06:** the gripper exclusion reads the dimension's own field name (`analysis/quality.py::_field`), never the `<topic>.` address prefix, so byte-identical payloads under `/joint_states` and `/left/gripper/joint_states` verdict identically (ADR 0018 amendment, EXP-0014 D1 closure).
10. ~~**An export job cannot be submitted through the API.**~~ **Closed 2026-10-06:** `ExportPayload.build_hash` required the canonical `bld_<64 hex>` shape instead of capping at 64 characters, so the hash the API itself publishes is accepted; a wrong-shaped value is refused at the boundary with a sentence instead of being queued and failed as `ExportBuildUnknown`. Found by submitting the API's own build hash from a live deployment, which every test had missed because the fixtures were short fakes (`bld_abc123`).
4. **The provisional 50 MB/s ingest target is not reachable by this design.** Container iteration plus JSON decode alone run at 42.6 MiB/s before the engine works at all ([EXP-0005](experiments/0005-mcap-ingest-flatten-plan.md)). Re-scoping to per-stage targets is an owner decision.
5. **The owner's system PostgreSQL on 5432 is unverified.** `just pg-up` covers development with an isolated cluster on 55432; that instance's superuser password is unknown and was never needed.
6. **Clean-clone validation and the history-wide secrets scan are done** (2026-09-28): a clean clone runs `just setup`, `just ci` and `just bench` green; no credential is in any of the 15 commits; `.env` was never tracked.

## 8. Open questions

- **Can the object core be extracted from real operator text?** This is now the load-bearing question for clustering, replacing the action view, and it is the one the shipped surface exposes rather than answers. The lexicons that strip verbs, colours, adjectives and locations recover the gold object on 100% of the synthetic corpus because that corpus was generated from them; on the 46 real LeRobot sentences there is no label to check against, and 37 of the 47 candidate Hub datasets did not resolve. The page reports the matched-verb rate so the gap is visible per run, but visibility is not accuracy. A learned extractor, or a larger labelled real sample, is the untried route.
- **Can the action view be solved at all?** Stage 2.5 answered no for a linear projection over general-purpose embeddings: the information is present (a pair probe reaches 0.784 held-out) but not expressible as a distance (threshold 0.724, projection 0.687, unprojected clustering F1 0.488). A representation trained for this task is the untried route.
- **Should the object view drop the verb entirely?** Answered on 2026-09-30: yes. Masking the verb before embedding removed all three verb-synonym false splits and made all 42 constructed clusters object-pure. The cost is that the view can now say nothing about actions at all, which is what the two-view design already implied.
- Fixture versioning for LeRobot at full episode size. The current fixture is the 203-frame tabular slice, not the video shards. For MCAP the fixture is a closed-form generator versioned by its arguments and SHA-256, so no download sits in the measurement path.
- What catalog migration and transaction or outbox strategy reconciles artifact writes with database state?
- What retry, lease and cancel semantics, and worker concurrency limits, land first?
- Do runtime metrics stay JSONL files, or move to a database or exporter once real query needs exist? Follow the ADR 0008 triggers; no speculative telemetry service.

## 11. Observability

- JSON logs and correlation IDs flow API to persisted job to worker to logs. Host telemetry covers CPU, RAM, disk and network, with nullable host fields on psutil errors and an AccessDenied test in the suite. **The `system_*` host/GPU gauges are now emitted on a runtime interval** (worker loop, every 60 s), which closed the last gap in the metric registry: a field the sampler could not read is omitted rather than zeroed, and a sampler that raises is logged as `host_sample_failed` and skipped.
- Runtime metrics: `jobs_queue_depth`, `jobs_queue_time_seconds`, `jobs_run_time_seconds`, `jobs_failures_total`, `pipeline_stage_duration_seconds`, `episodes_ingested_total`, `artifacts_written_bytes_total`, plus API request latency, catalog query timing, worker heartbeats, and the `monitor_*`/`incidents_*` family. **Every row in the registry is emitted by a call site.** JSONL sink at `DE_METRICS_PATH`. Labels stay low-cardinality; ids appear only in logs. Sink failures never break the pipeline.

### Lessons worth keeping

- "Pure core, unit-tested" is not coverage of a feature. Every defect in the end-to-end run was in the wiring around correct code, and 92% line coverage hid all five.
- Write the probe first. Chaos-harness and adversarial-probing defects were all found by a test or script that could fail, never by reading the code.
- A detector that reads the host reports the test machine, not the software. Six monitoring tests asserted a signal set while the resource detector read whatever else the laptop was doing; the suite went green or red with the developer's memory, and the chaos harness would have scored its campaign against it. Pin every input a rule reads, or the assertion is about the environment.
- A metric with units is not a metric with a scale. Plotting an L2 norm in source units put episodes at `1.0e8` beside joints at `0.02`; the chart was not misdrawn, it was showing nothing.
- Measure before optimizing, and attribute before claiming. `_dimensions` was 51% of ingest time; the disk was 65 ms and would have been blamed by order of magnitude.
- A `planned` row is a promise, not a note. Three stage-3 catalog rows named tests for behaviour that does not exist; closing them honestly meant restating what *is* implemented and naming the stage the rest belongs to, not building three subsystems to tick a box and not quietly leaving them unchecked.
- Say what is not automated. The production-like tier's value was entirely in the table listing what the OS scheduler and a human still do â€” `de gc` and `de migrate` do not exist, and a doc that implied otherwise would have been worse than no doc.
