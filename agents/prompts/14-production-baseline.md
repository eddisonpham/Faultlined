# Phase 14 — Production Baseline and User-Workflow Stress Campaign

Use the benchmark-engineer and implementer roles; coordinate with frontend-engineer for actual browser workflows. The goal is *not* to claim production readiness. Find failure boundaries, explain them with evidence, and turn each actionable issue into a tracked follow-up.

## Ground the simulated operator in product work

Personas: robotics data engineer, ML/policy engineer, evaluation engineer, platform engineer. Use cases must exercise actual UI/API/job/catalog/artifact paths: import real-format recordings, inspect task/quality and quarantine, review task-cluster proposals, save/select a slice, build/export a dataset, inspect lineage and job failures, recover after a process/DB interruption where safe. Record where the existing product does not support the next user step. Do not simulate an imaginary product path or treat mock-only tests as end-to-end evidence.

## Workloads

The scale labels refer to **episodes and their input/artifact bytes**, not synthetic request counts. Use at least one real LeRobot corpus and the committed real MCAP fixture where a real path exists. Never download or commit large source data unless asked. Preserve license/attribution and cite source revision/hash. Separate warmup from measurement; keep the scenario/config/seed stable; record all raw trial values and provenance; use ≥5 end-to-end repeats per scale when runtime allows. Smoke passes are not published measurements.

| Scale | Minimum target | Questions |
|---|---:|---|
| Small | 25–100 real episodes, one operator workflow | Can a user complete ingest → inspect → review/curate → export? Which errors block learning? |
| Medium | 1,000–5,000 episodes or all available real episodes if less, plus a representative long-tail task catalog | Do review, catalog queries, class-size rendering, and export stay bounded and understandable? |
| Large | 10,000+ episode records / realistic metadata cardinality, with artifacts representative of available inputs | Where do SQL latency, memory, page payload/render time, job queue, and artifact/disk costs bend or fail? Seed/generated catalog expansion is allowed only as a separately labelled scale dimension; do not call generated bytes/episodes real data. |

If real corpus size or owner data authorization blocks a target, report the exact gap and do not silently substitute generated data while retaining the scale label. Synthetic scale can diagnose catalog pressure separately.

## Personal diagnostic log

Use a local, gitignored file under `var/experiments/` with a per-run cap and rotation or overwrite; do not add a global persistent log table, ship it to the product, or store credentials, raw task text, robot payloads, dataset paths, user names, or personal information. The log is for the agent's own diagnosis only. Prefer low-cardinality event names and numeric values: run id, step, duration, status, item counts, response/render bytes, SQL operation label, RSS/CPU snapshots, and failure type. Hash/redact identifiers. Document the schema, cap, cleanup, and privacy rules before the first run.

## Measurement protocol

1. Define task scenarios and success predicates before running; record source/version/hash, seed, user persona, scale, and cleanup/reset plan.
2. Verify empty baseline and that each user step uses public CLI/API/browser surfaces. Record both successful and failed completion, dropped steps, retry/repair actions, and misinterpretations.
3. Capture wall-clock step latency, API p50/p95/p99, queue wait/run, rows/bytes, process RSS/CPU, disk, job failure/retry counts, SQL read latency, rendering/page payload size, review queue candidate/disposition counts, and export/hash validation. Mark unavailable signals rather than substituting zero.
4. Keep the diagnostic log private and bounded. Raw performance result files follow benchmark methodology and remain ignored under `benchmarks/results/`; summarized findings and provenance are documented in `agents/experiments/`.
5. Run a failure campaign separately from clean baselines: malformed file, duplicate submission, queue backlog, DB outage/restart, worker termination, disk pressure if safely injectable. Do not touch production data or arbitrary user queues.
6. Re-run each failing task isolated, then as part of the scenario, to distinguish product defects from shared test/system state.
7. Attribute before optimizing. Every proposed optimization names the measured symptom, a hypothesis, one changed variable, and a countermeasure ensuring output/lineage correctness.

## Stage-3 acceptance mapping

- Failure-mode catalog: audit every row against real test references; stage gate stays open while any is planned/partial.
- Observability: document queries for actual emitted logs/metrics, freshness and data gaps; do not claim absent host gauges.
- Production-like local tier: runbooks for start/stop, health checks, backup/restore drill, disk/artifact cleanup, and worker recovery on the supported Windows host.
- UI: inspect operator tasks for jobs, resources, experiments/runs, versions, failures, benchmarks, and artifacts; distinguish implemented from absent.
- Evidence: experiment record with provenance, raw result location, confidence/limitations, breakpoints, failure modes, and follow-ups. No baseline commit without owner authorization.

## Stop conditions

Stop before destructive reset, production service, external credentials, non-local account creation, data publication, or an irreversible operation. Ask the owner first. Do not change architecture, install dependencies, or claim stage completion without an ADR and evidence.
